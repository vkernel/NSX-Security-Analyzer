Automatic naming for single-IP static groups

One policy generates SZ-TZW-EXT-HST-<actual IP> directly from saved membership. No per-group ObjectType or Address proposals are needed.

These screenshots use synthetic inventory. The example contains 150 eligible hosts, including one deliberately incorrect name, plus five excluded definitions. No NSX changes are made by assessment or activation.

1 · Choose the policy scope

Use the single-host condition

Open Naming policies → New policy, or edit your existing manual static-host policy to convert it.

Category field and Category tag value are hidden and unused for this condition. It covers every eligible single-IP static group in the selected environment, regardless of its current name. Choose the fixed prefix to suit that scope.

2 · Name components

Use fixed text and an automatic address

OrderLogical fieldSourceValue / formatting
1PrefixFixed textSZ-TZW-EXT · UPPERCASE · Letters, digits, hyphens, dots and underscores
2ObjectTypeFixed textHST · UPPERCASE · Letters and digits
3AddressExplicit single host IPKeep case · IP address (IPv4 / IPv6) · maximum length 45 · Required checked

When you select Explicit single host IP, the editor sets the IP format, Keep case, Required and a sufficient length automatically. Leave its value mappings empty. The address is read from membership and cannot be replaced with a mapped or manually reviewed address.

If the editor starts with five default components, repurpose the first three and mark the two unused starter components Delete, then save. If converting the earlier manual policy, change ObjectType from a reviewed scope to Fixed text HST and change Address to Explicit single host IP. The five-component equivalent SZ / TZW / EXT / HST / Address also works.

3 · Save, preview, activate

Review the generated names before activation

  1. Click Save draft.
  2. Click Preview impact → Preview affected groups.
  3. Check the matching count, generated names and any policy conflicts. Environment totals are shown separately.
  4. Check the reviewed-impact acknowledgement and click Activate policy.

The draft example samples up to 100 saved groups. Full impact preview assesses all groups, including inventories larger than 100. Activation enables assessment only; it does not rename NSX objects.

If another equally specific policy covers these groups, the result is Ambiguous policy. Convert the existing policy or resolve the overlap before activation rather than leaving both active. Existing manual proposals are retained; this automatic source does not depend on them.

4 · Review outcomes

Names follow actual membership

Open Naming compliance → Compliant to see correctly named groups, or Needs attention → Name differs to find corrections. In the example, both .150 and .151 use one policy with no proposals. A group whose name ends in .249 but whose actual member is .149 receives a proposed name ending in .149.

Later collections automatically use the current saved IP definition. Unknown coverage remains provisional. Existing review workflow can still require attention after policy/evidence changes; automatic address extraction does not bypass review or cleanup controls.

Single-subnet groups

Use a separate policy with Exactly one explicit subnet, fixed ObjectType NET and source Explicit single subnet. It emits the canonical network with an underscore before the prefix length, such as SZ-TZW-EXT-NET-10.128.196.0_24. Follow the illustrated subnet guide.

Which definitions qualify?

  • One IPAddressExpression with one valid IPv4 or IPv6 host address.
  • A /32 IPv4 or /128 IPv6 host entry is accepted and normalized to the plain address.
  • Broader CIDRs, ranges, multiple entries (including duplicates), multiple expressions, nested groups, dynamic definitions, extended membership expressions, malformed entries and scoped IPv6 literals are excluded.

Excluded groups may match another policy or show No applicable policy. They are not silently classified as host groups.

Manual reviewed-values workflow remains available for other naming evidence.
